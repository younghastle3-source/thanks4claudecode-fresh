# Claude Code 活用スキル（Harness × Skills × Sub Agent）

## なぜ普通にAIを使うと破綻するのか

長期プロジェクトや複雑な開発でAIが失敗する3つの理由：

1. **コンテキスト消失** → 会話が長くなると前の文脈を忘れる
2. **品質の不安定** → 同じ指示でも確率的揺らぎで出力が変わる
3. **知見の非蓄積** → 試行錯誤で得た「正解」がセッションリセットで消える

**解決策 = 状態の外部化（Harness）× 判断基準のスキル化（Skills）**

---

## Harnessアーキテクチャ

### 中核コンポーネント

| コンポーネント | 役割 | ファイル例 |
|-------------|------|---------|
| **State（最重要）** | 現在の状態・進捗の単一真実源（SSOT） | `state.md` |
| **Playbook** | タスクの手順・受け入れ条件 | `plan/playbook-*.md` |
| **Hooks** | 処理の前後に自動実行されるルール | `.claude/hooks/` |
| **Skills** | 再利用可能なノウハウの関数 | `.claude/skills/` |
| **Sub-Agents** | 役割分担したAIエージェント群 | PM・レビュアー・コーダー |

### 実行フロー

```
依頼
 → Hooks起動（ルール適用）
 → PM（Sub-Agent）が要件整理
 → Playbook作成
 → レビュアー（Sub-Agent）が検証
 → State確認
 → 実装
 → 完了報告
```

## State管理（SSOT）

**最重要原則：state.mdが全ての真実**

- セッションが切れても state.md を読めば即座に続きから再開できる
- チャット履歴より state.md を信頼する
- 作業前に必ず state.md を確認する

```yaml
# state.md の典型構造
focus:
  current: product  # 今何をやっているか

playbook:
  active: plan/playbook-xxx.md  # 今のタスク

session:
  last_updated: 2026-03-20
```

**業務日誌（Daily Log）パターン**：
セッション終了時にその日の議論とブレイクスルーをAIに要約させ、次のセッション冒頭で読み込ませる。文脈を永続的に維持できる。

## Skills（ノウハウの関数化）

**Skillとは**：再利用可能な判断基準・ワークフローの部品

```
抽象化のポイント：
- 「何をするか」ではなく「どう判断するか」を定義
- マジックナンバー3：評価基準は3つの視点を持たせると品質が安定
- セッションをまたいで呼び出せる
```

**Skillが効果的な対象**：
- コンテンツ生成の型（台本・記事・投稿）
- 専門知識の適用（マーケ・営業・トレーニング指導）
- 品質チェックの基準（レビュー・添削）

**Skillが不要な対象**：
- 一度しかやらない作業
- コードの規約・アーキテクチャ（CLAUDE.mdに書く）
- 議事録・1on1の記録（URLで参照すればよい）

## Sub Agentの役割分担

人間が全部手動でやるのでもなく、AIに丸投げするのでもなく「協調（オーケストレーション）」が鍵。

### 代表的なエージェント構成

| エージェント | 役割 |
|------------|------|
| **PM Agent** | 要件整理・Playbook作成・タスク分解 |
| **CodeGen Agent** | 実装・コード生成 |
| **Review Agent** | 品質チェック・テスト（80点以上で合格） |
| **Critic Agent** | done_criteriaの達成検証（自己評価を防ぐ） |

### マルチエージェント・レビューの原則

AIは自己評価が甘い。「作るAI」と「レビューするAI（複数）」を分ける。
3つの異なる視点で合議させると客観的な品質チェックになる。

## Harnessの4ステップワークフロー

```
1. harness init   → プロジェクト初期化・State設定
2. plan           → PM Agentが要件整理・Playbook作成
3. work           → 実装・Sub Agentが自律実行
4. harness review → Critic Agentが完了条件を検証
```

---

## 非エンジニアでも使える実践原則

**「仕様駆動開発」で曖昧さを排除**：
- 「何となくこんな感じ」ではなく「受け入れ条件」を先に書く
- 完了の定義が明確なほど、AIの暴走・報酬詐欺（ハルシネーション）を防げる

**自然言語プログラミングの時代**：
- Pythonを書けなくても、「何を作るか」を正確に言語化できれば開発できる
- 重要なのはコーディング力より**ドメイン知識**と**指示の精度**

**先行者利益の期間は短い**：
- 現在のノウハウは約3ヶ月後には一般化する
- 「今すぐ作って出す」サイクルを回すことが最大の差別化

## よくある失敗パターンと対策

| 失敗 | 原因 | 対策 |
|-----|------|------|
| AIが前の指示を忘れる | state.mdを使っていない | 毎セッション冒頭でstate.mdを読ませる |
| 毎回品質がバラバラ | Skillが未定義 | 判断基準をSkillファイルに書く |
| 「完了」と言うが実は未完 | Criticがいない | done_criteriaを設けてCritic Agentに検証させる |
| 作業が止まる | Playbookがない | タスク開始前にPlaybook（手順書）を作る |
| 変更が意図せず広がる | CLAUDE.mdがない | 絶対ルールをCLAUDE.mdに定義する |

## このスキルの使い方

- 「開発が行き詰まった」→ Harnessの4ステップに戻る
- 「AIの出力が安定しない」→ Skillとして定義する
- 「長期プロジェクトで文脈が切れた」→ state.mdを更新してセッション再開
- 「完了判定が甘い」→ Critic Agentにdone_criteriaを検証させる
