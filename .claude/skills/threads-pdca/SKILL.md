# Threads PDCA スキル

> **参考アカウントの投稿から型を学び、自分の投稿に活かし、実績を振り返って次に繋げるための PDCA スキルです。**

## 参照リポジトリ（GitHub・おっくん自身のナレッジ）

このスキルで投稿案作成・分析・壁打ちを行う際は、`marketing` リポジトリ（github.com/younghastle3-source/marketing）を一次情報として参照すること。

1. `gh api repos/younghastle3-source/marketing/contents/AI_CONTEXT.md` を読み、リポジトリの構成・性格を把握する
2. 相談内容に関連しそうなファイル（Be Co Gym戦略、LP原稿、メイカラ講座メモ、SNS戦略メモ等）を `gh api` で探して読む
3. 一般論より、ここにある実体験・実データ・実際に学んだ内容を優先して回答に使う

## このスキルでできること

1. 参考アカウントの投稿をコピペで受け取り、**型ライブラリ（A〜J、随時拡張）に統合**する
2. 型ライブラリから型を選び、**投稿の下書き**を作る（狙った型は `references/type-log.md` に自動記録される）
3. `marketing` リポジトリの自動収集ログ（`Be Co Gym/threads-pdca-log/`）を読み込み、投稿後の実績（再生数・いいね・返信・リポスト・引用）を**自動で集計**する
4. 自動収集した実績を**週次/月次で集計**し、傾向を振り返って次の Plan に反映する
5. 読む側に**断らせる**（反応しない理由を出させる）ことで、下書きの精度と低反応型の原因分析を上げる

## 参照ファイル

- `references/pattern-library.md`: A〜J（随時拡張）の型の構造・出典・効く理由をまとめた型ライブラリ
- `references/my-posts-log.md`: 2026-08-20までの投稿実績を記録した**凍結アーカイブ**。以降のデータは自動収集ログ側にあるため、このファイルには追記しない
- `references/type-log.md`: 狙った型を記録する自動ログ。ワークフロー2で下書きを作った時点でスキルが自動追記する
- `references/conversion-log.md`: コンバージョン数を記録する手動ログ。ユーザーが気が向いたときに低頻度で記入する
- `references/draft-queue.md`: 投稿予定・検討中の下書きを保管する場所。投稿後の実績は `Be Co Gym/threads-pdca-log/` の自動収集ログ側に入るため、投稿したらこのファイルから該当エントリを削除・更新する（自動収集ログとの突き合わせは型ログ・凍結ログ側で行う）

## ワークフロー1: 新規アカウント分析（Research → 型ライブラリ統合）

発火フレーズ: 「Threadsの投稿分析して」「このアカウントの投稿を型にして」「参考アカウントの投稿貼るね」

ユーザーが参考アカウントの投稿をコピペで手渡してきたときに実行する。Threads API やスクレイピングは使わず、常にユーザーからの手渡しを前提にする。

1. 貼られた投稿を1件ずつ読み、`references/pattern-library.md` の A〜G のどの型に近いかを判定する
2. 既存の型と骨格が重複する場合は、その型のセクションに新しい特徴・言い回しを**統合**する（型を増やさない）
3. 既存のどの型にも当てはまらない新しい骨格の場合のみ、ユーザーに確認した上で新しい型として追加する
4. 統合・追加した内容には、必ずその投稿の**出典**アカウント名を明記する
5. `references/pattern-library.md` を更新し、変更点をユーザーに要約して報告する

---

## ワークフロー2: Plan（型選択 → 投稿の下書き作成）

発火フレーズ: 「Threadsの投稿作って」「今日の投稿の下書きお願い」「このネタで投稿書いて」

1. ユーザーから伝えたい内容・状況（日常/告知/振り返り 等）を受け取る
2. `references/pattern-library.md` を参照し、状況に最も合う型（A〜G）を1つ選ぶ（複数型の組み合わせも可）
3. 下記「断らせるチェックの手順」を実行し、読む側が反応しない理由を洗い出す
4. 選んだ型の「型の構造」に沿って**下書き**を作成する。verbatim CTA がある型（E）はそのまま流用してよい
5. 執筆時の一般注意（絵文字1〜2個・タメ口・地域名は告知系のみ）に沿っているか確認する
6. 下書きと「狙った型」をユーザーに提示し、`references/type-log.md` に日付・狙った型を1行追記する。投稿後の実績は翌週の自動収集ログ（`Be Co Gym/threads-pdca-log/`）に入る旨を伝える
7. 投稿URLが確定したら（投稿後の報告時など）`references/type-log.md` の該当行に投稿URL（permalink）を追記・更新する

### 断らせるチェックの手順（手順3 / 下書き作成前）

1. 読む側の**ペルソナ**を具体的に立てる（年齢・状況・過去の失敗体験・本音の疑いまで指定する）
2. そのペルソナを演じさせ、「この投稿に反応しない・参加しない理由」を**10個**、正直に挙げさせる
3. 出た10個を3分類する: ①今回の投稿で**先に触れる** ②**触れない**（コメント返信等で対応する） ③このペルソナは今回の**ターゲット外**と割り切る
4. Threads は短文なので10個全部は盛り込まない。①に選んだ1つ程度の理由だけを下書きに反映し、一番強い断り文句は文章の最初に置いて警戒を下げる

## 自動収集データの読み方（ワークフロー3・4の共通手順）

ワークフロー3（Check）とワークフロー4（Act）はどちらもこの手順から始まる。**読み取り専用**の手順であり、`marketing` リポジトリにも他のどのリポジトリにも書き込まない。Threads API のトークンを扱うリポジトリには一切アクセスしない。

### どこから・どうやって取るか

1. `marketing` リポジトリ（github.com/younghastle3-source/marketing）の `Be Co Gym/threads-pdca-log/` に、週次で `{YYYY-MM-DD}.json` が自動追加されている。パスにスペースが入るため `Be%20Co%20Gym` と URL エンコードすること
2. ファイル名は辞書順＝時系列順なので、一覧を取って `sort | tail -1` すれば最新が取れる

   ```bash
   F=$(gh api "repos/younghastle3-source/marketing/contents/Be%20Co%20Gym/threads-pdca-log" \
         --jq '.[].name' | grep -E '^[0-9]{4}-[0-9]{2}-[0-9]{2}\.json$' | sort | tail -1)
   ```

3. 本体を `gh api` で取得し、`content` を base64 デコードする

   ```bash
   gh api "repos/younghastle3-source/marketing/contents/Be%20Co%20Gym/threads-pdca-log/$F" \
         --jq '.content' | base64 -d
   ```

### 鮮度の確認

- 取得したらまず `fetched_at` をユーザーに提示する
- **`fetched_at` が今日から7日以上前なら、集計結果を出す前に「データが古い」旨を先に告げる**。週次 Routine が止まると `sort | tail -1` は古いファイルを返し続けるため

### 誰のデータか・JSON の形

- `profile.username` は `okkun_lifestyle`、`profile.followers_count` が倍率計算の分母になる
- 構造: `fetched_at` / `profile` / `posts[].meta{id, text, timestamp, permalink}` / `posts[].insight.data[]{name, values[0].value}`
- `insight.data[].name` は `views` / `likes` / `replies` / `reposts` / `quotes` の5つだけ。保存数・狙った型・コンバージョンはこの自動ログには存在しない（型は `references/type-log.md`、コンバージョンは `references/conversion-log.md` を見る）

### 閾値の出どころ

- 床・倍率・エンゲージ率の閾値は毎回 `Be Co Gym/threads-pdca-criteria.md` を `gh api` で読んで使う。**criteria.md 側が唯一の正であり、SKILL.md に閾値を書き写さない・ハードコードしない**
- `followers_count` が取れない/0の場合、倍率は**計測不可**として報告する（クラッシュさせない）

### 3指標の計算

- 床 = 投稿ごとの `views` が criteria.md の閾値以上か。「何件中何件が床を超えたか」で報告する（平均で判定しない）
- 倍率 = `views ÷ profile.followers_count`
- エンゲージ率 = `(likes + replies + reposts + quotes) ÷ views`

### データの落とし穴3点

1. `insight.data` が空配列の投稿が混ざる。**計測不可として集計から除外**し、「◯件中◯件で集計、◯件は計測不可」と件数を明示する。**0件として数えない**（0で数えると平均が不当に下がる）
2. 平均が**外れ値**1件に支配されることがある。**平均**だけで語らず**中央値**を併記する（例: 「平均は外れ値に引きずられている」と明示する）
3. `insight.data` が空の投稿は `meta.text`（本文）も `null` になり得る

### jq を書くときの注意（null 除算でのクラッシュ回避）

素朴な jq は `insight.data` が空配列の要素で null 除算クラッシュする。`.insight.data // []` と `select(` で必ずガードしてから集計する。

```bash
jq -r '[.posts[] | select((.insight.data // []) | length > 0)] | length' /tmp/threads-log.json
```

## ワークフロー3: Check（投稿後の自動収集ログ参照）

発火フレーズ: 「スレッズの実績見せて」「今週のスレッズどうだった」「Threadsの実績教えて」

投稿ごとの簡易チェックとして、直近の投稿実績を確認したいときに実行する。

1. 「## 自動収集データの読み方」の手順で最新の `{YYYY-MM-DD}.json` を取得し、`fetched_at` の鮮度をまず確認する
2. 直近の投稿（ユーザーが期間を指定しなければ最新1〜3件）について、床・倍率・エンゲージ率の3指標を算出する
3. `references/type-log.md` を投稿URL（permalink）で突き合わせ、狙った型が分かる投稿にはその型を添えて報告する
4. 床を超えたか・中央値との比較・計測不可件数を含めて、実績をユーザーに要約して報告する
5. 聞かれたら `references/conversion-log.md` にコンバージョンを追記する（催促はしない）

---

## ワークフロー4: Act（週次/月次の集計・振り返り）

発火フレーズ: 「Threadsの振り返りして」「今週の投稿まとめて」「月次でどの型が効いてるか教えて」

投稿ごとのチェックとは別に、週次/月次でまとめて振り返るときに実行する。

1. 「## 自動収集データの読み方」の手順で対象期間の自動収集ログを取得し、床・倍率・エンゲージ率を集計する
2. 各投稿を `references/type-log.md` と投稿URL（permalink）で突き合わせ、型が記録されていない投稿は `references/pattern-library.md` の型の構造と本文を照合して推定する（`pattern-library.md` は読み取り専用で参照するだけで、書き込まない・更新しない）
3. 型別に実績（床超え率・倍率・エンゲージ率）を集計し、効果が高い型・低い型の傾向を分析する
4. `references/my-posts-log.md`（2026-08-20までの投稿実績を記録した凍結アーカイブ）の気づき欄も参考に、長期的な傾向と照らし合わせる
5. 実績が低い型（特に E・F 型のような勧誘・理念発信系）が見つかった場合は、下記「低反応の型の原因分析」を実行する
6. 分析結果をユーザーに報告し、次の Plan（ワークフロー2）で優先すべき型を提案する

### 低反応の型の原因分析（断らせるチェック / オプション）

1. その低反応投稿を見る側の**ペルソナ**を具体的に立て（年齢・状況・過去の失敗体験）、そのペルソナを演じさせる
2. 「なぜこの投稿に反応しなかったのか、正直な理由」を**10個**挙げさせる
3. 出た理由から、次の Plan で避けるべき言い回しと追加すべき要素をまとめ、ユーザーへの**提案**として提示する
4. `references/pattern-library.md` の該当型の「効く理由」欄への注記候補として提示するに留め、ファイルへの自動書き込みは行わない

## 断らせるチェックのコツ（本音を引き出すコツ）

ワークフロー2・ワークフロー4 の「断らせるチェック」を実行するときは、以下に注意する。

- ペルソナは「客の立場で考えて」のような抽象的な指定では弱い。年齢・状況・過去の失敗体験まで具体的に指定する
- 反応しない理由は必ず**10個**と数を指定する（3個程度だと当たり障りのない建前しか出ない。10個だと後半に本音が出る）
- 出力が薄いと感じたら「今の回答は建前です。同じ質問に、本音で答え直してください」を追加で投げる
- 出てきた理由を全部真に受けない。過去に実際に言われた・見られた反応に近いものを優先し、教科書的すぎる指摘は優先度を下げる

---

## このスキルの使い方

1. ユーザーからの発火フレーズに応じて、上記4ワークフローのいずれかを実行する
2. 型の判断・下書き作成には必ず `references/pattern-library.md` を参照する
3. 実績の把握には `marketing` リポジトリの自動収集ログ（`Be Co Gym/threads-pdca-log/`）を参照する。狙った型・コンバージョンは `references/type-log.md` / `references/conversion-log.md` を、2026-08-20までの過去分は凍結アーカイブの `references/my-posts-log.md` を参照する
4. 参考アカウントの投稿は引き続きユーザーからの手渡しを前提にする。自分の実績データのみ `gh api` による自動取得に切り替える
