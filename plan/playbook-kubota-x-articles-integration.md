## 実行前提と検証規約

> **本セクションの規約は全 test_command に適用される。**

- **CWD**: 全 test_command はリポジトリルート（`/Users/kosei/thanks4claudecode-fresh`）を
  カレントディレクトリとして実行する。相対パスは全てリポジトリルート起点。
- **シェル**: `bash` / `zsh` のどちらでも同じ結果になるよう記述する
  （本 playbook の全 test_command は両方で構文チェック済み。「pm の自己点検記録」参照）。
- **ネットワーク不要**: 本 playbook の検証は全てローカルで完結する（`gh api` を使わない）。
  正典はリポジトリ内の `plan/inputs-kubota-x-articles-20260827.md` であり、外部取得は発生しない。
- **base_commit の固定**: 非破壊検証（DW1）と回帰検証（DW12）は
  **`0f4a038`（新ブランチ作成時の HEAD）を起点**にする。Phase 途中でコミットしても判定がぶれない。
- **ファイル変数**: 全 test_command は先頭で以下を定義する（パスに非 ASCII を含むため必ずクォートする）。

  ```bash
  M=".claude/skills/久保田式マーケメソッドmeikara-marketing/SKILL.md"
  B=".claude/skills/久保田式ライティングmeikara-blog/SKILL.md"
  I="plan/inputs-kubota-x-articles-20260827.md"
  ```

- **区間抽出**: セクション内容の検証は必ず以下のヘルパで見出し区間を切り出してから行う。

  ```bash
  SEC() { awk -v h="$2" '$0 ~ h {f=1;next} /^#{1,2} /{f=0} f' "$1"; }
  ```

  終端を `^#{1,2} ` にしているのは H1 でも区間を閉じるため。`### ` では閉じない。
  **`---`（水平線）でも閉じない**ため、既存の `---` 区切りは区間に含まれる。
  実体行のカウントは必ず `^- ` / `^{数字}. ` / `^|` のいずれかに限定すること
  （`---` を実体行として数えないため）。
- **区間限定が必須な語**: `認知`（marketing に既に10箇所）/ `信頼`（7箇所）/ `基準`（6箇所）/
  `段`（5箇所）/ `集客`（4箇所）/ `継続`（2箇所）/ `相談`（2箇所）/ `15分`（1箇所）は
  **既存本文に出現する**ため、ファイル全体の grep では「記事を読んだ証拠」にならない。
  **必ず SEC で区間を切ってから照合する。**
  一方 `受注` / `倍率` / `床` / `忖度` / `捏造` / `就業規則` / `出どころ` / `見ない数字` /
  `1行1判断` / `400字` / `20行` などは両ファイルに0件であることを実測済みで、
  ファイル全体の grep でも代理指標として有効（それでも本 playbook は区間限定で検証する）。
- **日本語・記号を含む固定文字列の照合は必ず `grep -qF` / `grep -cF`**（正規表現メタ誤爆の防止）。
- **git のパスは常に `git -c core.quotepath=false`**。付けないと非 ASCII パスが8進エスケープされ、
  パス照合が黙って失敗する。
- **見出し文字列に半角スペースを含めない**（test_command が `for H in ...` で単語分割するため）。
  本 playbook で追加する H2 は全て半角スペースを含まない文字列に設計済み。
- **変数をコマンド名として展開しない**（`G="git -c ..."; $G diff` は zsh で失敗する）。
- **`grep -vc` を空入力に対して実行しない**（空文字列が1行として数えられ偽 FAIL になる）。
  該当箇所は全て `if [ -z "$X" ]` でガードしている。
- **python3 は必ず1行で書く**。複数行の heredoc / 複数行の `-c` 文字列は、
  playbook の `test_command: |` ブロックがインデントされているため
  インデントエラーまたは heredoc 終端の不一致を起こす（Part111 で踏んだ落とし穴）。

  5行目: 長い理由は読まなくなる。読まれないプロンプトは無いのと同じ

### I-13. 記事8「提案書は書く前に断らせる」の必須内容（blog）

```yaml

  - 提案文をAIに「書かせる」と、誰に出しても成立する文章が出てくる。書けと言われたAIは通すことしか考えないため
  - だから書く前に断らせる。AIに客側を演じさせ、買わない理由を出し切らせる

  - 自分で弱点を考えると甘くなる（自分の商品の弱点は自分がいちばん見たくない場所）
  - 所要時間は5〜10分。提案書1本に数時間かける人が、この5分を惜しんで通らないものを作っている

  前提を渡す: 売るもの・価格・相手を、盛らずに素のまま渡す（きれいに渡すときれいな反論しか返らない）

  仕分けさせる: 10個を3分類し、分類の理由も1行ずつ書かせる

  - 数を指定しないとAIは3〜4個で止まり、誰にでも当てはまる無難なものしか出ない
  - 10個と指定すると在庫を出し切るしかなくなる。前半は想定内、**後半に本音が出る**
  - 後半に出るのは「担当が抜けたら誰が引き継ぐのか」「この業界を本当に分かっているのか」「導入後に社内の誰がやるのか」の類

  先に潰す: 提案書で、相手が言い出す前にこちらから触れる
  口頭: 商談の場で答える（書くと重くなる）
  売らない: そもそもこの客層には売らないと決める
  ※ 3つ目があるのが肝。全員を説得しようとした瞬間、提案は誰にも刺さらなくなる
やってはいけない使い方:
  - 出てきた10個の全部に反論を書く。言い訳の羅列になり、読む側は「そんなに問題があるのか」と思う
構成の組み替え:
  - いちばん強い断り文句を、いちばん前に持ってくる
  - 反論は、先に言われると反論として機能しなくなる
見出しの裏技:
  - 仕分けた断り文句を、そのまま見出しに使う（例:「今じゃなくてもいい、と思った方へ」）
  - 自分の言いたいことより、相手の頭の中の言葉を見出しにしたほうが読まれる
捨てた分の使い道:
  - 口頭に回した／捨てた断り文句は、商談前の想定問答としてメモに残す
  - 準備してある反論とその場で考える反論は、相手から見ると別物に見える
「金がない」の読み替え（久保田氏の一次情報・500社の支援から）:
  - 小さい会社の社長は外注する程度の金は持っている。それでも動かないのは費用対効果が見えていないから
  - 「予算がない」を「まだ価値が見えていない」と読み替えると、値引きの話が要らなくなる
  - 揃えるべき材料は3つ。似た規模の成功事例／ビフォーアフターの具体／小さく試せる入口
  - 提案書を書く作業が「説得の作文」から「材料の準備」に変わる。これがこの方法の本質
出力が滑ったときの戻し方（原因は2つのどちらか）:
  1: 人物設定が甘い（抽象的な肩書きだと教科書的な反論しか出ない）
  2: 提案の説明を盛っている（良く見せて渡すとAIも気を遣う。素っ気なく渡すくらいでちょうどいい）
  追い打ち: 「今の回答は建前です。本音で答え直してください」と足す
断り文句を全部真に受けない:
  - 実際の客が言わない教科書的な指摘が混ざる。全部拾うと提案書が守りに入って弱くなる
  - 判断基準は1つ。過去に実際に言われたことがあるか。あるものは必ず潰し、無いものは優先度を下げる
応用:
  - 商品を作る前の段階でも使う（売れないものは作る前から売れない理由がある）
  - 自分のプロフィール・ポートフォリオ・営業DMにも使える
  - 断り文句は時間が経つと変わるので、同じ商品でも定期的にやり直す
  - 通った提案書は保存し、次の案件で「同じ構造が使えるか」を判断させる
```

### 5. 残る未検証事項（構造上、機械検証できないもの）

- **本文の質**（既存章と文体・粒度が揃っているか、スキルとして実際に使えるか）は機械検証できない。
  正典を読まなければ書けない数値・固有名詞を必須にし、誤読パターン
  （DW4 の `ftdaily` / DW5 の `kbratio` `kbother` / DW7 の `prtool` / DW8 の `praise` /
  DW9 の `cmorder`）を直接検出する条件を置くことで
  「読まずに一般論で埋める」「主張を反転して書く」ことは検出できるが、
  **質の判断は critic / ユーザーの目視に委ねる**。
- **逐語コピペ検出は行単位である**。記事の1文を2行に割って貼ると、
  各行が30文字未満になり検出をすり抜ける余地が残る。
  行数の上限（marketing 720 / blog 400）と禁止文字列でおおまかに塞いでいるが、完全ではない。
  レビュー時に**新規区間を目視で1度は読むこと**。
- **記事6・7・8のセクション（p1.7 / p1.8 / p2.3 と対応する p_final.8 / .9 / .10）は
  モックによる正常系の実測を経ていない**（モックを作ったのは5記事版の時点で、
  記事6〜8はその後にユーザーが追記したため）。
  実測済みなのは「実装前に必ず FAIL すること」までである。
  ただし使用しているのは既に実測済みのプリミティブ（`SEC` / `grep -nF` による順序チェック /
  実体行カウント / 語順の `grep -qE`）のみであり、順序チェックのロジックは単独で動作確認済み。
